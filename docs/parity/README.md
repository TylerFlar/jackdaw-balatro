# Parity ledger

The parity ledger is the checklist that proves the Rust engine covers every piece of gameplay
logic in the real game, Balatro 1.0.1o (`balatro_source/`, gitignored and proprietary). It is
generated by [`scripts/parity_ledger.py`](../../scripts/parity_ledger.py), which parses the Lua
with a real parser (`luaparser`). Each row is one auditable unit of the source: a function, an
entity-specific branch, an RNG site, a joker-context call, a queued event or a game entity.
Reviewers fill in where each unit lives in Rust and which test covers it.

- [`ledger/`](ledger/): one table per scope file, e.g. [`ledger/card.lua.md`](ledger/card.lua.md).
- [`gaps.md`](gaps.md): the gap register. G01–G51 are gameplay gaps found during planning; B01–B14
  are the non-gameplay fixes.
- [`smods-diffs.md`](smods-diffs.md): where the live game (Steamodded, BalatroBot) differs from vanilla; `smods-diff` rows cite its ids.
- This README: commands, row kinds, statuses, the review protocol and the generated summary.

## Commands

```sh
# Regenerate after a generator change; review data is merged back by row id.
uv run --no-sync --with luaparser==4.2.0 python scripts/parity_ledger.py generate

# Fail (exit 1) if a ledger file is out of sync with the source, a field is invalid, a gap id is
# unknown, a stale row remains or the summary below is outdated.
uv run --no-sync --with luaparser==4.2.0 python scripts/parity_ledger.py check

# The final gate: also fail while any row is still unreviewed.
uv run --no-sync --with luaparser==4.2.0 python scripts/parity_ledger.py check --strict

# Why a function was, or was not, pre-marked n/a.
uv run --no-sync --with luaparser==4.2.0 python scripts/parity_ledger.py explain '^Card:draw$'

# Offline checks (no Lua source or luaparser needed; part of the normal test suite).
uv run pytest tests/parity_ledger
```

- The script needs `balatro_source/` (or `--source DIR`) and refuses to run unless its
  `version.jkr` starts with `1.0.1o`. CI has no Lua source, so it runs only the offline tests.
- `luaparser` is not a project dependency: `--with` adds it for one run and `--no-sync` leaves the
  project environment untouched. The script needs luaparser 4.x; all twelve scope files parse
  with 4.2.0, so no fallback tokenizer is needed.
- `generate --prune-stale` also deletes stale rows that carry no review data.

## Scope

| file | rows come from |
|---|---|
| `card.lua`, `blind.lua`, `back.lua`, `tag.lua`, `cardarea.lua` | every top-level function |
| `functions/state_events.lua`, `common_events.lua`, `misc_functions.lua`, `button_callbacks.lua` | every top-level function |
| `game.lua` | `Game:init_game_object`, `Game:start_run`, `Game:delete_run` and the `Game:update_*` state handlers, plus `Game:update` (the state dispatcher, which also moves `SELECTING_HAND` to `DRAW_TO_HAND` when the hand is empty) and `Game:init_item_prototypes` (the prototype tables and pool ordering); entity rows from `P_CENTERS`, `P_BLINDS`, `P_TAGS`, `P_STAKES` and `P_SEALS` |
| `challenges.lua` | one entity row per challenge |
| `functions/UI_definitions.lua` | only functions with a gameplay side effect: an RNG draw, `create_card`, `level_up_hand`, a game-state ease (`ease_dollars`, `ease_chips`, `ease_discard`, `ease_hands_played`, `ease_ante`, `ease_round`; `ease_value` and `ease_colour` are visual tweens) or an assignment into `G.GAME` |

Functions defined inside another function belong to the enclosing function's rows.

## Row kinds

| kind | one row per | subject | context |
|---|---|---|---|
| `function` | top-level function definition | `name(params)` | — |
| `branch` | `if`/`elseif` arm that names a specific entity, inside a branch-scope function | the entity names, then the arm's condition | enclosing conditions |
| `rng` | seeded draw (`pseudorandom`, `pseudoseed`, `pseudoshuffle`, `pseudorandom_element`), call of a helper that draws for its caller, or unseeded `math.random` | the call | enclosing conditions |
| `context_call` | `calculate_joker`, `eval_card`, `trigger_effect` (decks), `calculate_seal`, and `apply_to_run` with a table literal (tag contexts) | method and context keys; values are shown for literals and `G.*` areas | enclosing conditions |
| `event` | `G.E_MANAGER:add_event` | the literal `trigger`/`blocking`/`blockable` (and queue/front) arguments, then `→` the calls its function makes | enclosing conditions |
| `entity` | joker, tarot, planet, spectral, voucher, booster, back, enhancement, edition, base card, seal, blind, tag, stake and challenge | `Type: name (key)` | the functions that name it, or `not named in code (data-driven)`; challenges also list their rules and starting items |

Details:

- **Branch scope.** The functions the plan lists: `Card:calculate_joker`, `use_consumeable`,
  `can_use_consumeable`, `set_ability`, `add_to_deck`, `remove_from_deck`,
  `calculate_dollar_bonus`, `calculate_seal`, `get_end_of_round_effect`, `apply_to_run`, `open`,
  `redeem`, `set_cost`, `get_chip_*`, `get_p_dollars`, `get_edition`; every `Blind:` method;
  `Back:apply_to_run` and `trigger_effect`; `Tag:apply_to_run` and `yep`; and `evaluate_play`,
  `end_round` and `evaluate_round`. On top of those, gameplay functions whose named arms carry
  entity rules: `Card:update` (per-frame joker values), `sell_card`, `set_edition`, `set_seal`,
  `get_nominal`, `get_id`, `is_face`, `is_suit`, `check_use` and `highlight`; `Tag:set_ability`;
  `CardArea:update` and `draw_card_from`; `new_round`, `draw_from_deck_to_hand` and
  `discard_cards_from_highlighted`; `draw_card`, `get_current_pool`, `create_card` and the
  `reset_*_card` helpers; `mod_chips` and `get_blind_amount`; the `can_select_card`,
  `check_for_buy_space`, `buy_from_shop` and `reroll_boss_button` callbacks; and
  `create_card_for_shop` and `create_UIBox_blind_choice`.
- **Naming an entity.** A condition names an entity when it contains: `X.name`, `X.effect`,
  `X.seal`, `X.key` or `X.center_key` compared with a string that is an entity's name, key or
  effect; `find_joker('…')`; `X.name:find('…')`; `G.GAME.used_vouchers.v_…`,
  `G.GAME.banned_keys[…]`, `G.GAME.used_jokers[…]` or a `G.P_*` table entry; an edition flag
  (`X.edition.foil` and so on); a deck config key (`self.effect.config.<key>`); a blind debuff
  key (`self.debuff.<key>` in `blind.lua`); or a challenge or stake rule
  (`G.GAME.modifiers.<key>`). Literals are checked against the parsed prototype tables, so
  `args.key == 'BACKSPACE'` does not count.
- **RNG helpers.** `create_card`, `create_playing_card`, `poll_edition`, `get_pack`,
  `get_current_pool`, `get_next_tag_key`, `get_next_voucher_key`, `get_new_boss`,
  `random_string`, `reset_idol_card`, `reset_mail_rank`, `reset_ancient_card`,
  `reset_castle_card` and `CardArea:shuffle` draw on their caller's behalf, and the caller picks
  the stream key, so each call site is an `rng` row. A `pseudoseed(…)` passed straight into
  another draw is part of that draw's row. `math.random` inside `play_sound` or speech-bubble
  arguments (sound pitch, quips) is not listed.

## Columns

- **id**: stable and semantic, `<file>/<kind>/<function>[/<anchor>]/<slug>[#n]`. The kind is one
  of `fn`, `branch`, `rng`, `ctx`, `event` or `entity`. The anchor is the innermost enclosing
  entity arm, for example `hallucination`. The slug is the entity names (branch), the function and
  stream key (rng), the method and context flags (ctx), the trigger and first call (event), or
  type and key (entity). `#n` numbers repeats within one function in source order. Line numbers
  are never part of an id.
- **lua**: `file:start-end` in `balatro_source/`.
- **kind**, **subject**, **context**: generated, as described above. A context chain lists the
  enclosing conditions, outermost first, joined by ` & `. `else(A … B)` is the else arm of an
  `if`/`elseif` chain whose first and last conditions were A and B. `[event]` means the code runs
  later, inside a queued event.
- **status**, **rust**, **test**, **gap**, **notes**: filled in by reviewers. These are the only
  columns to edit by hand; `generate` rewrites the others.

## Statuses

| status | meaning |
|---|---|
| `unreviewed` | nobody has checked the row yet |
| `ported` | the Rust code exists; `rust` names it, e.g. `crates/jackdaw-core/src/jokers.rs::hiker` |
| `verified` | ported and covered by a test; `test` names it |
| `gap` | a known behaviour gap; `gap` lists ids from [gaps.md](gaps.md) |
| `smods-diff` | vanilla and Steamodded/BalatroBot differ here; `notes` names the deviation-catalog entry |
| `n/a-ui` | no gameplay effect: rendering, animation, sound, input, menus |
| `n/a-meta` | profile, unlock, achievement or settings logic with no gameplay effect |

## Review protocol

1. Read the Lua at `lua`, then the Rust (and, while it exists, the Python oracle).
2. When the Rust exists, set `ported` and fill `rust`. When a test covers the unit, set `verified`
   and fill `test`; `cargo llvm-cov` over the tapes and fuzzing must show the unit executed.
3. When behaviour differs, add a gap to [gaps.md](gaps.md) (or reuse one), put its id in `gap` and
   set `gap`. The fix lands in the Python oracle first, with a regression test citing the Lua
   lines, then in Rust; the row then moves to `ported`/`verified` and keeps the gap id in `gap` as
   history. Update the gap's own status in gaps.md as well.
4. For `n/a-ui`, `n/a-meta` and `smods-diff`, say why in `notes`.

`check` enforces: a valid status; at least one gap id on a `gap` row; every gap id defined in
gaps.md; `rust` on `ported` and `verified` rows; `test` on `verified` rows; unique ids; no stale
rows; ledger files in sync with the source; and an up-to-date summary. `check --strict` also
requires that no row is still `unreviewed`.

## Pre-marked rows

`generate` pre-marks a row `n/a-ui` or `n/a-meta` only when a conservative heuristic shows it has
no gameplay effect, and records the reason in an `auto:` note:

- **Functions.** The function writes no game state and calls no in-scope function that might.
  In addition, it must be UI, animation, sound or localization code by name (`draw`, `hover`,
  `juice_up`, `align`, `set_sprites`, `generate_UI*`, `play_sound`, `localize`, …), profile or
  unlock code by name (`set_joker_usage`, `inc_career_stat`, …), or code that never reads game
  state and touches only UI state (`G.C`, `G.ROOM`, `children`, `T`, …) or profile state
  (`G.PROFILES`, `G.ACHIEVEMENTS`, …).
  - Game state means `G.GAME`, `G.STATE`, the card areas, `G.playing_cards`, the `G.P_*` tables,
    and card, area and blind fields (`ability`, `base`, `edition`, `seal`, `debuff`, `facing`,
    `cost`, `cards`, `card_limit`, `highlighted_limit`, …). In `Game` methods, `self` counts as
    `G`.
  - Calls between in-scope functions are resolved by name (methods by method name), as a greatest
    fixed point.
  - Legality checks (`can_*`) are never pre-marked.
- **Rows inside a pre-marked function** inherit its status.
- **Events** whose body only animates, plays sound, waits, or sets UI fields and input locks.

Pre-marks are suggestions. To overrule one, change the status and replace the `auto:` note with
your reason. A row whose review columns hold only generator output keeps following the generator,
so a better heuristic reaches it. That means: `unreviewed` with no note, or an `auto:` note, with
`rust`, `test` and `gap` all empty. Anything a reviewer types makes the row theirs.

## Stale rows

When the generator stops producing an id (for example after a generator change renamed it),
`generate` keeps the old row and its review data under "Stale rows" at the end of the file, and
`check` fails until it is resolved. Copy the review data to the new row, then delete the stale
row.

## What the source cannot tell

Some behaviour is not determined by the source alone:

- the iteration order of `pairs()` over `G.GAME.hands` (To Do List, Orbital Tag, The Ox
  tie-break);
- three unseeded `math.random` calls (the first-shop Buffoon pack, and the Charm and Meteor Tag
  mega packs), which are `rng` rows in `get_pack` and `Tag:apply_to_run`;
- `unique_val`, which is approximated by creation order.

These are frozen as shared constants and confirmed with live captures (see the plan).

The Lua source is proprietary. The ledger quotes only identifiers and conditions of at most 100
characters (72 inside a context chain), never code.
